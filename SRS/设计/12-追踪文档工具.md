## v2.1 说明作源（2026-10-10 用户提出，当日实现）

**核心洞察**：说明文档本身是"浓缩了追踪关系"的文档——其用例表（与记录用例表完全同构）的追踪关系行就带**大纲章节号+项名+项标识**，说明+记录 按 用例标识 join 就能出报告表，**不必回溯大纲**。

| tab | 主文档 | 配对文档（自动识别大纲/说明） | SRS 列 |
|-----|--------|------------------------------|--------|
| 说明追踪 | 大纲 **或说明**（自动识别） | — | 大纲源自动 / **说明源留空**（实证：说明文档里没有 SRS 数据，全文唯一"需求规格说明"痕迹是静态步骤正文文本） |
| 报告追踪 | 测试记录 | 大纲 **或说明** | 同上 |
| 回归说明 | 回归说明 | **仍仅大纲**（回归说明自身编号不能替代大纲章节号，配对到说明项目时明确报错） | 大纲源自动 |

- **自动识别**：先按大纲解析（找「测试项及方法」章），失败转说明解析（用例表特征）——用户不选，传什么识别什么；建档 sourceType 按识别结果（新增 `spec` 类型）
- **说明作源的数据来源**：大纲章节号/项名/项标识 = 说明用例表追踪关系行（`测试需求分析：6.2.1.4.2.2 XXX / 测试需求标识：XQ_SU_YKBS`）；测试类型 = 说明 heading 栈；SRS 留空
- **vmerge 空列通配**：合并键忽略空值列——说明源报告表 SRS 全空时，同测试项的行仍按大纲侧列整块合并；一行有值一行空自然不合并
- **真实样例验证**（02 说明 V1.10 + 03 记录 V1.00）：93 行、SRS 零残留、大纲章节号全对齐、vMerge 92/338、validate 通过；说明追踪表 110+ 例说明文档上传自动识别成功
- 提取 `extractReturnSpec` 为通用"说明族文档解析器"（回归说明/说明共用：items+cases{用例名/标识/用例章节号/追踪关系三元组/typeName}）

## 实测定稿（与初稿设计的差异，2026-10-10 实现轮确认）

1. **对齐加"去尾序号"兜底层**：记录/回归说明里多用老工具的无序号写法（`YL_DC`），大纲转换按 03 规则生成 `YL_DC_001`——对齐先精确匹配 caseId，失败再去掉尾部 `_NNN` 用基形匹配（真实样例 93 例中 87 例靠此层命中）
2. **真实数据不一致是常态**：记录手写标识与大纲推导标识可能缩写不同（样例 6 例 `YL_SU_ZLQQ_*`/`YL_GUI_BCDGUI_*`）——告警点名留空，不猜不拦
3. **执行结果自动推导三要素**（记录表逐行勘察确认）：步骤行"通过与否"列 + "执行状态"行 + "问题单标识"行——全通过且已执行且无问题单 → "通过"；否则留空人工判断；备注=问题单号（无 → "--"）
4. **回归说明用例章节号实证**：= 用例表所在最近标题的自动编号（文档审查用例 6.1.1、项下用例 6.1.2.1.1），复用大纲 numbering 还原机制
5. **回归说明的测试项表与大纲同构**（`extractItemTable` 直接复用）、用例表与记录用例表同构（`parseCaseRecordTable` 共用）——两个新解析器薄
6. **vMerge 渲染走后处理**：docxtemplater 循环无法条件化单元格属性——渲染完成按 rows 的 span 标记做 XML 手术（restart/continue + 续行清空文本），HTML/剪贴板通道用 rowspan
7. **四套模板程序化生成**（脚本 `.claude/tmp/追踪模板四套.ts`，从旧追踪文档模板抽取 tblPr/表头/数据行原型重建），officecli validate 4/4；旧"追踪文档模板.docx"删除，打包脚本清单更新为四套

## 定位

从四类源文档生成**四类追踪表**，用户复制（HTML 直贴 Word）或下载 docx，贴入各自目标文档。替代人工从大纲/记录/回归说明手工整理追踪关系。

与工具一共享：大纲解析层（[02-解析层](02-解析层.md)）、转换层、项目库（[09-本地数据管理](09-本地数据管理.md)）、异常文件拦截（[06-错误处理](06-错误处理.md)）。

## 四类追踪表（真实样例定稿）

### 总览

| # | tab 名 | 目标文档位置 | 列数 | 输入 | 每行粒度 |
|---|--------|------------|------|------|---------|
| 1 | 大纲追踪 | 大纲附件2「测试项与软件需求规格说明对照表」 | 6 | 大纲 | 每测试项一行 |
| 2 | 说明追踪 | 测试说明「需求的可追踪性」章 | 8（双层表头） | 大纲 | 每用例一行 |

### 1. 大纲追踪表（6 列）

样例：大纲附件2（tbl[62]，两层表头）。

| 列 | 来源 |
|----|------|
| 序号 | 生成时编号 |
| 需求来源-软件研制任务书 | 恒 "--"（大纲无此数据，人工填） |
| 需求来源-软件需求规格说明 | 大纲"追踪关系"行解析章节号（无则 "--"） |
| 测试项标识 | 测试项表格标识格（XQ_DC） |
| 测试类型 | 项所属类型名（文档审查/功能测试…） |
| 备注 | "/" |

### 2. 说明追踪表（8 列，双层表头）

样例：说明 V1.10「需求的可追踪性」（tbl[126]）。= **v1 已实现的 traceRows 8 列升级**：

| 分组（跨列） | 列 | 来源 |
|----|----|------|
| （序号，独立列） | 序号 | 生成时编号 |
| 软件需求规格说明 | 章节号 / 章节描述 | 大纲"追踪关系"行（无对应写 "/"） |
| 软件测试大纲 | 大纲章节号 / 测试项名称 / 测试项标识 | 解析层（Word 自动编号还原）+ 测试项表格 |
| 测试用例 | 测试用例名称 / 测试用例标识 | 用例标题 + 转换层生成 |

- **纵向合并（vmerge，本轮核心升级）**：连续行同 SRS + 同测试项 → 软件需求规格说明两列 + 大纲三列合并（w:vMerge restart/continue；HTML 预览用 rowspan）
- **双层表头**：真实文档表头两层（分组跨列 + 子列），v1 模板是单层 8 格 → 模板手术改双层
- 排除用例不入表（与工具一口径一致）

### 3. 报告追踪表（11 列，双层表头）——"文档多一点"的那个

样例：报告附件2（tbl[25]，92 行 × 11 列）。

| 分组（跨列） | 列 | 来源 |
|----|----|------|
| （序号，独立列） | 序号 | 生成时编号 |
| 软件需求规格说明 | 章节号 / 章节描述 | **大纲（必须输入）**按标识对齐补齐——记录里无此信息，不配大纲信息不全 |
| 测评大纲 | 章节号 / 测试项名称 / 测试项标识 / 测试类型 | **记录用例表"追踪关系"行**（"测试需求分析：6.2.1.1 文档审查 / 测试需求标识：XQ_DC"）+ 记录 heading 类型上下文 |
| 测试用例 | 测试用例标识 / 名称 / 执行结果 | 记录用例表"测试用例名称/标识"行；**标识带步骤号范围**（`YL_SU_ZLPA_001-001~005`，步骤数 = 记录表步骤行数，识别规则实现时按样例定）；执行结果见下 |
| （备注，独立列） | 备注 | **记录"问题单标识"行**（PT_R2657_1；无问题单 → "--"） |

- **执行结果列**：测试记录**无结论格**（每张用例表：记录N → 用例名/标识 → 追踪关系 → 综述 → 步骤行 → 测试人员/监测人员 → 问题单标识 → 备注，全程无"通过/未通过"）→ 默认"**通过**"，预览表里可逐条编辑后再复制/下载；**有问题单的行默认留空**（提示人工判断）
- **纵向合并**：同测试项连续行 → SRS 两列 + 大纲四列（含测试类型）合并
- vmerge 样例实证：同一测试项 5 个用例（参数查询/新增/修改/删除/异常）的前 7 列合并成一块

### 4. 回归说明追踪表（9 列，双层表头）

样例：回归说明 V1.00「需求的可追踪性」表7-1（tbl[26]）。

| 分组（跨列） | 列 | 来源 |
|----|----|------|
| （序号，独立列） | 序号 | 生成时编号 |
| 软件需求规格说明 | 章节号 / 章节描述 | **大纲（必须输入）**按标识对齐；回归说明自身"追踪关系"行样例为"隐含需求"（无章节号） |
| 测评大纲 | 大纲章节号 / 测试项名称 / 测试项标识 | **大纲（必须输入）**按项标识对齐补章节号；项名/标识从回归说明测试项表解析 |
| 测试用例 | 用例章节号 / 测试用例名称 / 测试用例标识 | **用例章节号 = 用例在回归说明文档里的编号**（如 6.1.2.1.1，解析回归说明编号结构）；名称/标识从回归说明用例解析 |

- 回归说明解析规则（新解析器）：测试项表结构与大纲同构（测试项名称/标识/优先级/追踪关系）；用例标题形态、用例章节号提取规则**实现时按样例定**
- **纵向合并**：同说明追踪表

## 交互设计（用户拍板的 tab 流向）

进入追踪工具 → **第 1 步顶部四 tab**：`大纲追踪 | 说明追踪 | 报告追踪 | 回归说明`，各自上传对应文档：

```
大纲追踪   ：上传大纲.docx
说明追踪   ：上传大纲.docx
报告追踪   ：上传测试记录.docx ＋ 大纲.docx（都必须——SRS 两列只能来自大纲）
回归说明   ：上传回归说明.docx ＋ 大纲.docx（都必须——大纲章节号与 SRS 两列只能来自大纲）
```

- **大纲的提供走项目库优先**：大纲项目本就共用项目库（[09](09-本地数据管理.md)），从最近大纲项目点选即用；项目库里没有再上传新大纲（上传即自动建档，后续可复用）。**两份文档都就位才进第 2 步**
- 解析概要 + 问题清单照常展示，不拦截生成
- 最近项目列表**按 tab 的源类型过滤**（大纲 tab 显示大纲项目、报告 tab 显示记录项目…）
- 第 2 步：预览（双层表头 + vmerge 渲染，大数据量截前 200 行）+「复制表格」+「下载 .docx」——沿用 v1 通道

## 项目库扩展

- 项目元信息加 `sourceType`：`outline`（大纲，现有）/ `record`（测试记录）/ `returnSpec`（回归说明）
- 内容哈希寻址、建档、免上传重开逻辑不变（解析入口按类型分派）
- 工具一最近项目列表只显示 `outline` 类型（不受影响）

## 技术要点

- **解析器新增两个，大纲解析零改动**（黄金基线 37/110/528 安全）：
  - 记录解析器：扫描"记录N"用例表（识别用例名/标识行、追踪关系行、问题单行、步骤行数）+ heading 类型上下文
  - 回归说明解析器：测试项表（同大纲同构）+ 用例清单 + 用例章节号（自动编号还原，复用 numbering 机制）
- **跨文档标识对齐**：join 键 = 测试项标识（XQ_*）/ 用例标识（YL_*）；对不上的行留空 + 告警（不拦截）
- **vmerge 渲染**：docx = `w:vMerge`（首行 restart / 续行 continue）；HTML 预览与剪贴板 = rowspan——两通道同一合并模型
- **双层表头模板**：四类表头各一套，从真实样例 1:1 复刻列宽与合并结构；说明追踪表在现有模板上手术（单层 8 格 → 双层）
- 大文档口径：预览截 200 行、复制/生成不受限，沿用 [10-大文档处理](10-大文档处理.md)

## API 设计

```
POST /api/trace/generate
  body: { traceType: 'outline'|'spec'|'report'|'returnSpec',
          primary: {name, hash},            // 大纲 / 记录 / 回归说明（按类型）
          alignOutlineHash: string,         // 大纲项目（record/returnSpec 时必须；SRS/大纲章节号唯一来源）
          resultOverrides?: {caseId: string}// 报告追踪：执行结果的人工编辑值
        }
  ← { ok, doc: { name, sizeKB, base64?, path? }, rows: TraceRowVMerge[] }
```

- 解析入口按 primary 类型分派（outline 走现有 /api/parse 链路；record/returnSpec 走新解析器）
- 落盘交付、水位保护沿用现有规则

## 错误处理

- 异常文件六类拦截原样生效
- 报告/回归说明 tab：主文档零用例 → 禁用生成 + 提示
- 标识对不上的行：告警清单（"N 行未在大纲中找到对应项，需求列留空"），不拦截
- 执行结果人工编辑仅存内存（随生成请求发送），不入编辑存档（报告追踪一次性使用）
