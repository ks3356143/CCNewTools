## 二、输入（2026-11-22 定稿：三件，回归说明不传）

1. **测试大纲**（项目库或上传）——类型/项数/用例数、追踪关系与需求描述原文；
2. **首轮测试记录**（项目库或上传，上传自动建档）——执行/通过判定、问题数据；
3. **回归测试记录**（可选，仅现场上传不入库）——表38 列4 的回归轮次结果。
   回归说明不作为输入：批注本身指向大纲；其内容全部由大纲推导（工具三同源）；少一件少一层匹配与不一致风险。

## 三、v1 实现

- **核心** `src/core/report/build.ts`：`buildConfData(parsed, first, reg, params)` → 每个大纲测试项一行（**全量需求**，非仅回归项）。判定口径与工具三一致（只认步骤「通过与否」）；复用 `matchRow` 三级容差匹配（起导出）。
  - 列4 四态：`首轮测试通过`（项下用例首轮全过）/ `回归测试通过`（首轮有未过、回归全过）/ `回归测试未通过` / `首轮测试未通过`（首轮有未过且未传回归记录，出 REPORT_REG_MISSING）/ `未测试`（项下用例首轮均未见记录）。
  - 列3 精简规则（v1 占位，待用户反馈调）：≤400 字原样；超出按段落边界截到约 360~420 字，尾加「……（内容过长，已截断，详见需求规格说明）」；解析层只读文字不读图，去图天然满足。
  - 配套性告警（告警不拦路）：REPORT_REG_MISSING / REPORT_REG_FAIL / REPORT_ITEM_UNTESTED / REPORT_CASE_NO_RECORD / REPORT_NO_MATCH，聚合点名前 6 项。
- **模板** `模板/报告模板.docx`（手术脚本 `.claude/tmp/报告工具/模板手术.ts`）：剥 18 条批注（标记 + comments part + ContentType + 关系）；表38 数据行四格植 `{#confRows}{no}|{source}|{metric}|{result}{/}` 行内循环。**坑**：xmldom `serializeToString` 自带 XML 声明，拼在原声明后成双声明 → validate 报 Malformed，剥掉再拼。

## 五、v2 七点反馈落地（2026-11-22 用户七问，全部批注位置铺开）

用户定义口径：**用例数 = 用例表的步骤行数**（每个步骤行算一个用例）；**静态类型 = 文档审查/静态分析/代码审查/代码走查**，其余为动态测试。

1. **八段统计段落**全部植 docxtemplater 标签（就地手术 `.claude/tmp/报告工具/批注铺开手术.ts`）：1.7.3 全量类型清单+类型数+测试项数、1.7.4 设计用例数、2.1 问题分类、2.2.4.1.1 文档审查设计/执行/不通过、2.2.4.4.1 动态用例数+类型清单（**不含静态四类**）、2.3 b/c/d、「无未执行测试用例」条件导语。注意坑：b)/c)/d) 前缀是自动编号不是文字，锚点不能用它。
2. **表26**：11 个样例类型行收敛为 `{#t26Rows}` 循环（动态类型逐行：设计步骤行 vs 首轮执行/未执行/通过/未通过步骤行）+ 小计变量行。
3. **表33/表34**：逐格上 q33/q34 变量（等级×类型交叉）。**等级/类型无字段依据** → 按样例报告「均为一般问题」惯例默认归类：总数=首轮不通过步骤行，**全部计入「一般问题 / 其他问题」**；归零=回归记录核验通过数、遗留=其余；出 REPORT_LEVEL_ASSUMED 告警请人工核对。表34 类型列为固定四种（文档审查/功能测试/性能测试/人机交互界面测试），其它类型的未通过只进总计（REPORT_T34_UNMATCHED 告警）。
4. **表38 列4 新规则**：首轮全通过 → 该项各用例在首轮记录的**「期望结果与评估标准」文字**（解析层只读文字，图天然不进；超 400 字同列3 截断）；首轮有不通过 → **「经过测试符合要求」**（用户拍板不写未通过）；用例全无记录 → 「未测试」。记录解析层为此新增 stepExpects/stepActuals 步骤文字列（纯增量，工具二/三不受影响）。
5. **界面**：统计条改步骤行口径（大纲 X 表/Y 步 · 执行 Z 步 · 不通过 W 步 · 归零/待核验）；首轮有未通过且未传回归记录 → 显著横幅「建议上传回归测试记录后重新生成」。
6. **测试项数口径（待确认）**：样例报告 1.7.3 与 1.7.4 同为 4582 → 「测试项」暂按与用例同口径（步骤行）填；若应为测试项表数（如 WQ 229）需改一处。

## 六、未匹配探针 → 两层智能匹配（2026-11-22 用户质疑"28 项肯定能找到" + "把程序做智能点"）

逐用例探针 + 深挖发现的真问题与两层智能修复：

1. **撞号错配（真 bug）**：真实大纲同一 itemId 撞号在两个章节、各有一行同 caseId（XQ_SU_ZSPG 在 .4.2.35 设置功能与 .7.1.3.5 知识评估功能测试各有一个 YL_SU_ZSPG_001）——`matchRow` 多命中盲取第一行，把知识评估/知识库统计的记录结果记到了设置功能头上，自己反成「未测试」。修复：**同标识多命中按「用例名」消歧**（记录表「测试用例名称」格与大纲用例名一致才是同一行的硬证据；名不吻合回退首个，REGRESS_DUP_CASEID 告警继续兜底）——改在共享 matchRow，工具三/四同时受益。
2. **改版漂移重定位**：旧标识在新大纲给了别的功能（XQ_SU_PJRT 旧=关键词检索 → 新=凭据检索），旧记录表名/追踪名仍是关键词检索。新智能层：标识配到的项名与记录追踪名不符、而「追踪项名 + 用例名」能**唯一**锁定另一行 → 重定位过去 + `REPORT_MATCH_BY_NAME` 告警点名（凭据检索→关键词检索）。歧义（如「类型选择和类型支持」跨多项同名）不硬配。
3. **实证效果**：未测试 28 → **25**、首轮通过 185 → **188**；关键词检索表38 行由「未测试」变为记录用例文字；剩余 25 项全部是「协同生产/加固/检测/验证/环境/服务」类**大纲拆项**（V1.10 把粗粒度项拆成 16+ 细子项，记录按旧粒度执行的合并大用例步骤文字覆盖各子功能，但没有任何行的项名+用例名能唯一对上）——属大纲改版固有形态，保持未测试+告警；用户按新版大纲执行的新记录会全部对上。
