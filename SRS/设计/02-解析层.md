# 02 解析层

> 状态：**已与用户确认**（2026-09-29），规则已在真实大纲上**全量验证通过**

## 职责

读入测试大纲 `.docx`，输出领域模型。不含任何业务规则。

## 一、范围界定

**只处理"测试项及方法"这一节**（当前大纲里是 6.2）。

定位方式：找标题文本匹配 `测试项及方法` 的 heading，从它开始，到下一个 level ≤ 2 的标题为止。

范围外的内容（测试依据、测试环境、测试组织、附录的检查单与对照表等）全部跳过。

## 二、标题与章节号

### 章节号是 Word 自动编号，不是正文文字

大纲里的 `6.2.1.4.1.1` 这类编号**不存在于段落文本中**，是 Word 按 `numbering.xml` 自动生成的。

还原方式：

1. 解析 `numbering.xml`，建立 `numId → abstractNumId → 各级 numFmt / start` 映射
2. 遍历段落，读其 `w:pPr/w:numPr`（`w:numId`、`w:ilvl`）
3. 按 `ilvl` 维护计数器：遇到某级标题则本级 +1，其下所有级别清零

本大纲全部标题共用 `numId=1`、`numFmt=decimal`、各级 `start=1`，计数器法已验证与文档目录一致。

### 标题嵌套不固定（**关键**）

实测 37 张测试项表格所挂标题的层级：

| 挂载层级 | 数量 | 例子 |
|---------|------|------|
| level 4 | 3 | `6.2.1.1 文档审查`、`6.2.1.2 静态分析`、`6.2.1.3 代码审查` |
| level 5 | 17 | `6.2.1.5.1 A星有效载荷控制指令生成准确率测试` |
| level 6 | 17 | `6.2.1.4.1.1 A星指令参数管理` |

三种嵌套形态同时存在：

```
6.2.1.1 文档审查                     ← level 4，表格直接挂这
6.2.1.4 功能测试                     ← level 4（测试类型）
  6.2.1.4.1 A星模板功能测试           ← level 5（中间层，没有表格）
    6.2.1.4.1.1 A星指令参数管理       ← level 6，表格挂这
6.2.1.5 性能测试                     ← level 4（测试类型）
  6.2.1.5.1 A星有效载荷控制指令生成准确率测试   ← level 5，表格挂这
```

**因此每个测试项要记录一条完整的"标题路径"**（从测试类型到测试项的所有祖先标题），而不是只记一个标题。

- 测试类型 = 最近的 level-4 标题
- 测试项 = 表格前面最近的那个标题（4/5/6 级都可能）
- 路径示例：
  - 文档审查 → `[{lvl:4, num:"6.2.1.1", text:"文档审查"}]`
  - A星指令参数管理 → `[{lvl:4, "6.2.1.4", "功能测试"}, {lvl:5, "6.2.1.4.1", "A星模板功能测试"}, {lvl:6, "6.2.1.4.1.1", "A星指令参数管理"}]`

## 三、识别测试项表格

表格第 1 行第 1 格文本为 `测试项名称` 即命中。

本大纲里该特征唯一（37 张表全部符合，无其他表误命中）。

## 四、提取字段

按**行标签**取值而不是按行号，格式微调（多行少行）不会崩：

| 行标签 | 取值 |
|--------|------|
| 测试项名称 | 第 2 格 → 测试项名称；第 4 格 → 测试项标识 |
| 追踪关系 | 第 2 格 |
| 测试项描述 | 用例综述的来源 |
| 测试方法 | 用例标题 + 步骤 |

（表格固定 7 行：测试项名称 / 追踪关系 / 需求描述 / 测试项描述 / 测试方法 / 充分性要求 / 通过准则）

## 五、段落提取（**容易踩的坑**）

同一张表格里，"测试方法"单元格的段落有两种渲染形态：

| 测试项 | 单元格结构 |
|--------|-----------|
| 文档审查 | 7 个普通段落（步骤编号 `1）2）` 是**字面文本**） |
| 静态分析 | 2 个普通段落 + **自动编号列表** |
| 代码审查 | 2 个普通段落 + **自动编号列表**（4 项） |
| 普通类型（功能测试等） | 全是普通段落（编号是字面文本） |

也就是说**静态类型的步骤在 Word 里是自动编号列表**，正文里根本没有 `1）` 这两个字——用正则 `^\d+）` 切分会直接漏掉整段。

解析时必须：

1. **同时处理普通段落和列表项**，并保持文档顺序
2. **剔除自动编号的渲染标记**（否则文本会被污染成 `46）编程准则检查：…`）

> 实测代码审查的列表自动编号显示为 `46）47）48）49）`——大纲自身的编号定义有问题，不影响我们（说明文档的序号由模板重新编）。

## 六、切分用例与步骤（**核心规则**）

### 用例切分

"测试方法"单元格里，匹配下面正则的段落 = **用例标题行**，开启一个新用例：

```
^\d+\s*[.、]\s*(.+?)\s*[（(]\s*([A-Za-z]{2}_[A-Za-z0-9_]+)\s*[)）]\s*$
```

- 第 1 个捕获组 = 用例名称
- 第 2 个捕获组 = 测试需求标识（如 `XQ_SU_ZLPA_SU01`）

### 综述来源

"测试项描述"单元格里：

- 若同样有 `n.名称（标识）` 标题行 → 标题行**后面紧邻的段落**是该用例的综述
- 若整个单元格只有一段、没有标题行 → 这段是**该测试项下所有用例共用的综述**（18 个测试项属于这种）

### 步骤切分

标题行之后的段落按下列规则切成步骤：

```
1. 匹配 n.名称（标识）的段落        → 开启一个新用例
2. 标题行后第一段若以「：」结尾       → 引导句
3. 以 m） 开头的段落                → 新步骤
4. 以「：」结尾的段落（非首段）      → 新步骤，其后的非编号段落并入
5. 其余段落：
     上一段以「；」结尾  → 并入上一步骤
     上一段以「。」结尾  → 新步骤
     否则                → 并入上一步骤
```

**引导句处理**：仅 2 个用例有（文档审查、代码审查），计划**并入第 1 步的开头**，避免信息丢失。（待用户最终确认）

## 九、大纲变种实测与补充规则（2026-09-30，BCD星大纲）

拿到另一颗星的完整大纲（`文档S/大纲变种.docx`，同为 37 张测试项表）做了全量普查，暴露出以下与 A星大纲不同的形态。**以下规则均已按实测结果定稿**（除 9.5 待样例验证）。

### 9.1 悬空小标题行（**必须丢弃**）

"测试方法"格里会出现以"："结尾的**独立小标题行**，后面紧跟编号步骤，本身不带任何内容。实测 A星大纲**没有**这种行；BCD 变种的 参数管理 表里有 3 处：

```
2）在参数列表下方的查询输入框中输入参数标识，……；
查询标识：                ← 悬空小标题行（无作用）
3）在查询输入框中输入参数名称，……；
```

甚至有 `XXXX：`（同事忘了删的占位符）。现行"以「：」结尾的段落 → 新步骤"规则会把它误切成一个**空步骤**。

**判定**：以"："结尾、非用例标题行、**其后直到下一个步骤/标题之间没有可并入的正文**（即按现行规则切出来的步骤内容为空）。

**处理**：不生成步骤，整行丢弃，收集一条**信息级提示**（"已忽略小标题行：查询标识："），界面上可在解析概要里看到，不算告警不算错误。

> 这样判定比"短于 N 个字"更稳：只丢弃真正切不出内容的行，正文里以"："结尾的真步骤不受影响。

### 9.2 测试项描述没有子项 → 所有用例共用综述（已实测确认）

BCD 变种 37 张表里有 11 张（人机交互界面、安全性、余量、强度、恢复性、安装性、兼容性等）"测试项描述"格**只有一段、无子项标题行**，而"测试方法"里有 1~5 个用例 → 这段描述就是该测试项**所有用例共用的综述**。与第六节规则一致，已被实测确认。

### 9.3 测试项描述与测试方法的子项数量可能不一致（**以测试方法为准**）

实测 BCD 变种"宏动作与指令模板映射管理"：描述格 8 个子项，方法格只有 7 个（"修改异常功能"在方法里没写）。

**处理**：用例一律以"测试方法"里的标题行为准；描述格的子项综述按**需求标识**匹配到用例，描述里多出来的子项**忽略并记一条告警**；方法里有用例但描述里找不到对应综述的，回退用共用综述（若存在），都没有则综述留空并记告警。

### 9.4 标识不一致的形态扩展

第八节的兜底（用例标识 vs 测试项标识不一致）之外，实测发现**描述格与方法格之间**也会有笔误：BCD 变种 准确率测试 的描述格写 `XQ_AC_SCZQ_AC01`、方法格写 `XQ_AC_SCZQL_AC01`（多个 L）。规则不变并扩展：**一切以"测试方法"里的用例标题标识为准**，描述格标识只用于综述匹配，匹配不上就按 9.3 处理。

### 9.5 通过准则格的两种形态（**待样例验证**）

实测的两份大纲里，"通过准则"格**全部为空**（"充分性要求"格是两句固定模板话，两份一致，无需解析）。但用户告知：有的同事编写的大纲会把通过准则**逐条对应测试方法的每个步骤**。因此解析层增加一条规则：

- 若"通过准则"格有逐条内容，且条数与该用例步骤数对应（或带 `n）` 编号），则将其作为各步骤**期望结果与评估标准**的来源（替代关键词切分）；
- 否则维持第五节的关键词切分。

每张表记录"期望结果来源：通过准则 / 方法文本切分"，界面上展示。**此规则目前没有真实样例验证，拿到该形态的大纲后必须先跑一遍再定稿。**

### 9.6 标题层级跳级（规则已覆盖，实测确认）

BCD 变种里性能测试、接口测试、边界测试、安全性测试等是 level-4 标题**直接跳到 level-6** 的测试项（中间没有 level-5），说明"记录完整标题路径"的规则是对的，按现有方式处理即可。

## 十、参考实现

验证用的原型脚本思路（可直接作为实现的骨架）：

1. 用 `fflate` / `pizzip` 解 docx 的 zip
2. 解析 `word/document.xml`、`word/numbering.xml`
3. 单遍扫描 body，按文档顺序产出「标题」和「表格」两种 token
4. 对表格：按行标签取值 → 按上述规则切用例和步骤
