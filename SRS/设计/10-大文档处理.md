## 一、背景与实测证据

### 1.1 问题

第三方测试大纲体量超出预期：内网实测的《R2661软件测评大纲-分册2》**zip 33.5MB、解压后 document.xml 42.2MB**（XML 压缩率高，正文比整个压缩包还大）。这是**已经拆过分册**的产物——出纲方的正常交付粒度就是这个量级，工具必须原生支持。

现行上限（v1.1.5 起）：zip 总大小 100MB 防呆、**document.xml 解压后 20MB**——分册2 被 20MB 正文上限拦下。

### 1.2 为什么不能直接提上限：实测数据

2026-10-08 用合成等规模大纲（document.xml ≈ 42MB）跑全链路实测：

| 阶段 | 现状实现 | 实测结果 |
|------|---------|---------|
| 解析 | xmldom 全量 DOM（整份 XML 一次性建成节点树） | 内存飙升持续数分钟未完成 |
| 渲染 | docxtemplater 全量循环（整份输出 XML 字符串拼接） | 内存飙升 |
| **合计** | — | **两个 bun 进程合计 24GB+（12.9GB + 12.7GB），本机内存占满，用户叫停** |

**结论：内存大头不是业务数据（几十 MB），而是"整份文档 × 几十倍"的结构性放大**。直接把上限提到 60/100MB 只会让内网机器在更长的挣扎后崩掉（单文件服务进程崩掉连错误都看不到）。必须改架构。

### 1.3 内存账（现状逐环节）

| # | 环节 | 现状做法 | 内存量级（42MB 正文） |
|---|------|---------|---------------------|
| 1 | zip 解压 | fflate unzipSync 全量 | ~200MB（XML 字符串 + zip 结构） |
| 2 | DOM 构建 | xmldom 解析整份 document.xml | **2~6GB**（几百万节点 × 每节点 JS 对象数百字节） |
| 3 | 解析遍历 | extractOutline 走 DOM 产出领域对象 | 数百 MB（含 #2 的 DOM 常驻） |
| 4 | 转换 | convertToTemplateData 再产一份 | 数百 MB |
| 5 | 渲染 | docxtemplater 全量循环拼接输出 XML | **2~4GB**（输出 50~100MB 字符串 × 内部多份拷贝） |
| 6 | 交付 | base64 编码 → JSON 响应 → 前端 blob | ×1.33 再加序列化拷贝，又是 GB 级 |

## 二、目标与非目标

**目标**

1. document.xml 解压后 **100MB** 以内的大纲可以完整走通 解析 → 核对 → 生成（覆盖分册2 的 42MB 并留一倍以上余量）
2. 全链路内存峰值 **< 1GB**（8GB 内网机器无压力），解析与生成全程界面有进度反馈、服务不崩
3. 生成产物**落盘到数据目录**，界面与控制台横幅告知路径——浏览器不再承载大文件传输
4. 老文档（≤20MB）行为完全不变，黄金统计基线逐项一致

**非目标**

- 不追求"任意大小都能吃"——超过新上限仍拒绝并给明确文案（拆分对 200MB+ 的文档依然是正确建议）
- 不改变核对交互形态（左树 + 单用例编辑）——数千用例下该交互天然成立（见 5.5 观察项）
- 不换模板体系（docxtemplater 保留，改造调用方式而非重写渲染）

## 三、方案总览：三支柱

```
大纲 .docx (zip ≤200MB)
   │
   ▼
【支柱一】分块解析 ChunkReader ── document.xml 按顶层元素切块，逐块 DOM 化即用即弃
   │        （替代 xmldom 全量 DOM，砍掉 2~6GB 的最大爆点）
   ▼
领域对象 items/cases（全量常驻 ~200-300MB，可接受，不分批）
   │
   ▼
【支柱二】分批渲染 + body 合并 ── 按测试项分批过 docxtemplater，每批即用即弃，
   │        只合并输出 document.xml 的 body 片段，最后统一打 zip
   │        （替代全量循环拼接，砍掉 2~4GB 的第二大爆点）
   ▼
【支柱三】落盘交付 ── 产物写入 数据/生成/<项目>/，界面展示路径与大小，
            控制台横幅同步提示（替代 base64 下载，浏览器零大内存）
```

**被否决的方案**（避免重复讨论，决策记录同步 [技术栈选型](../技术/技术栈选型.md)）：

| 被否方案 | 否决理由 |
|---------|---------|
| SAX 流式解析全替换（saxes 等事件式解析） | 解析规则（标题栈/表格判别/编号还原）全部迁移重写，回归风险大、新增依赖；收益与支柱一等价。留作分块方案不够时的后备 |
| 只提高上限不动架构 | 实测 24GB+ 爆内存，见 1.2 |
| 前端强制"每批 ≤150 用例"分批交互 | 解析侧分块后内存已解决，全量领域对象放得下，无需把数据结构改成"卷"；
  交互侧数千用例的浏览器性能留作观察项（5.5），卡了再上分页载入（批大小即用户建议的 150） |
| 分批渲染结果落盘暂存、最终拼接文件 | 累积 body 字符串 50~100MB 在内存可接受；磁盘暂存引入原子性/清理问题，
  200MB+ 输出的场景出现时再升级（升级路径见 5.4） |

## 四、支柱一：分块解析（ChunkReader）

### 4.1 核心思想

业务解析真正消费的只是**顺序结构**：段落（文本/numPr/outlineLvl/pStyle）和表格（行→格→段落）。全量 DOM 保留的是整棵树，而树中 99% 的节点在消费完一个顶层元素后就是死重。

**把 document.xml 按 body 顶层子元素切成块，逐块 DOM 化、处理完即丢**——单块 DOM 峰值 = 一个测试项表格的 DOM（几 MB 级），业务解析逻辑（outline.ts 的标题栈、表格判别等）**几乎原样保留**。

### 4.2 切块算法

document.xml 的 body 顶层子元素只有 `<w:p>` 与 `<w:tbl>`（Word 输出形态），按标签深度配对切分：

```
扫描器（单次线性扫描，42MB 约 200~500ms，内存 O(当前块)）：
  i = body 内容起点
  while 未到 </w:body>：
    遇 <w:p → 顶层段落：找配对 </w:p>（段落内不嵌套段落，直接找最近的；
            但需跳过 <w:tc>…内的误导？不——顶层 p 不在表格内，</w:p> 即自身闭_tag）
    遇 <w:tbl → 表格：深度计数配对（<w:tbl 深度+1，</w:tbl> 深度-1，
            归零处即本表格结束——容错嵌套表格）
    产出 { kind: 'p'|'tbl', xml: 切片 }，i 跳到块尾继续
```

安全性依据：XML 文本节点里的 `<` `>` 已转义（`&lt;` `&gt;`），标签边界扫描不会被正文内容干扰；Word 不输出 CDATA 到 document.xml（构建器与真实样本均已验证形态）。

**分块开关阈值**：document.xml ≤ 20MB（现行上限）走原全量 DOM 路径（零行为变化、老文档零风险）；> 20MB 自动切 ChunkReader 分块路径。两条路径共用同一套消费代码（4.3），统计与告警必须逐字节一致——用黄金基线四份样本 + 42MB 合成样本断言。

### 4.3 接入方式（改动面）

- `docx.ts` 新增 `readDocxChunks(data): { kind, node } 迭代器`（或回调式 `forEachChunk`）：
  内部做 4.2 切块，每块 `new DOMParser().parseFromString(块xml)` 后交给消费者，消费者返回后释放
- `outline.ts` 的 `extractOutline` 主体循环不变，仅把"遍历 body 子元素"改为"逐块取"：
  ```ts
  // 现状：for (const node of kids) { ... }
  // 改后：for await (const chunk of readDocxChunks(...)) { const node = chunk.node; ... }
  ```
- `numbering.xml`、`styles.xml` 体量小（几 MB 内），**保持全量 DOM 不变**
- textOf/expandSoftBreaks/标题栈/编号还原等本轮及此前全部解析规则**原样生效**——它们都工作在"段落/表格"粒度，与块来源无关

### 4.4 阶段一验收标准

- 83 项自动化测试全绿（老路径）；新增分块路径测试：同一份样本分别走两条路径，解析结果 JSON 逐字节一致
- 黄金基线四份真实样本统计与可疑数逐项一致（37/110/528 可疑 4 等）
- 42MB 合成样本解析：内存峰值 < 800MB、耗时 < 60s（当前爆 24GB 跑不完）
- 服务端日志记录"大文档分块解析"模式与耗时

## 五、支柱二+三：分批渲染、合并与落盘交付

### 5.1 为什么渲染必须分批

实测大头之二。docxtemplater 对整份模板 XML 做循环展开，几千用例的输出 document.xml 达 50~100MB，内部字符串拷贝放大 20~40 倍。**分批后每批只有几百用例的输出（几 MB），即用即弃**。

### 5.2 分批渲染与合并设计

**批的切分单位 = 测试项**（生成文档的天然结构边界，与生成日志"逐测试项表格"一致）；批大小按输出量自适应（目标每批输出 document.xml 片段 ≤ 5MB，约 100~300 个用例/批）。

```
1. 模板骨架渲染：docxtemplater 渲染模板中循环区之外的部分
   （封面、说明章头、用例清单表、追踪表、sectPr）——小数据量，一次完成
2. 循环区分批：cases 按 5.1 分批，每批：
   a. 以同一模板文件新建独立 PizZip/docxtemplater 实例
   b. 只喂本批 cases（模板循环标签原样生效，样式继承与单批渲染完全一致）
   c. 取输出的 document.xml，抽取循环区对应的 body 片段（首尾定位标记法，见下）
   d. 片段追加进累积 body 字符串；本批全部结构即刻释放
3. 组装：骨架 document.xml 的循环区占位处插入累积片段 → 写回第 1 批的 zip 包
   （numbering/styles/media/页眉页脚与单批产物完全一致）→ 落盘
```

**循环区定位**：不靠字符串猜测——在改造模板时于循环块 `{#cases}` 前后埋入**不可见锚点段落**（如 `<w:p><w:r><w:t>_CT_BEGIN_</w:t></w:r></w:p>`，渲染后按锚点切片；锚点段落最终删除）。锚点在两份模板（说明/记录）的循环区各埋一对。

**必须专项验证的清单**（合并语义正确性，P2 的主要工作量所在）：

| 项 | 风险 | 验证方式 |
|----|------|---------|
| 自动编号跨批 | 记录文档"记录1/记录2"等编号要求每用例重启；跨批合并后 numId 相同，编号是否延续取决于 numbering 定义 | 单批与分批产物 XML 比对 + Word 打开人工核对首尾用例编号 |
| 书签配对 | 模板含书签（v1.0.1 修过配对），批间书签 ID 可能重复 | 分批时对批内书签 ID 做全局重映射（偏移 = 前批累计数），产物 XML 断言无重复 ID |
| 题注/域（SEQ） | Word 打开时域自动刷新重算，理论无风险 | 产物 officecli validate + 人工打开抽查 |
| 字体/样式 | 各批同模板同 styles.xml，理论一致 | 产物 XML 与单批产物逐段比对（v1.1.0 时期已有"逐字节比对"方法可复用） |

**回退开关**：用例数 ≤ 500（或输出 < 10MB）时走**现状整体渲染路径**（一次 docxtemplater）——小文档走成熟路径零风险，分批只在大文档触发。开关阈值可配置。

### 5.3 落盘交付（用户折中方案的正式化）

**产物不再走 base64 下载**（浏览器端 ×1.33 内存 + JSON 序列化拷贝全免）：

- 产物写入 `数据/生成/<项目id12>/测试说明-生成.docx`、`测试记录-生成.docx`（每次生成覆盖，文件名沿用现行固定名；项目目录语义与 [09-本地数据管理](09-本地数据管理.md) 对齐）
- `/api/generate` 响应改为 `{ ok, files: [{ name, sizeKB, path }] }`——响应体仅几百字节
- 界面完成页：两个文件卡片（名称/大小/完整路径 + "已保存到上方目录"提示），保留「重新生成」「返回修改」；**小文档（≤10MB）额外保留下载按钮**（习惯延续），大文档只展示路径
- 控制台横幅同步打印：`生成完成：…\数据\生成\<项目>\测试说明-生成.docx（27.3KB）`
- 生成日志补每批进度：`分批渲染 2/6 批（第 101~200 号用例）`

### 5.4 上限调整与文案

| 项 | 现值 | 新值 | 依据 |
|----|------|------|------|
| document.xml（解压后） | 20MB | **100MB** | 分册2 的 42MB × 2.4 余量；峰值内存按 42MB 实测线性外推 ≈ 1~1.5GB，可承受 |
| zip 总大小 | 100MB | **200MB** | 大纲以图片为主的极端形态 |
| 超限文案 | "大纲规模异常庞大，请拆分后分批导入" | 保留同款逻辑，数值随上限更新 | 200MB+ 已超出该工具合理边界，拆分依然是正确建议 |

**升级路径**（预留，本期不做）：若未来出现输出 > 200MB 的场景，累积 body 字符串改为磁盘暂存（`数据/生成/<项目>/暂存/`，分批追加写、组装后删除）——接口设计时把"片段消费器"抽象出来即可平滑替换。

### 5.5 前端规模化（P3 已实施，2026-10-09）

数千用例推入 Vue store 的性能风险点：树渲染节点数、用例清单表、响应式代理开销。三屏交互"单用例编辑"模式本身不吃总量的亏。

**P3 实测（42MB / 29686 例，Playwright 真实交互计时，验证轮树修复之后的残余卡顿点）**：

| 操作 | 实测 | 评价 |
|------|------|------|
| 打开项目：API（解析+恢复）→ 前端切屏+首帧 | 6.9s + ~1.5s | 大头是服务端解析（P1 范畴）；前端 1.5s 一次性成本，可接受 |
| 展开极端层（"功能测试"下 14843 项，截断渲染 200） | ~180ms | 良好——验证轮 v-if+折叠+截断生效 |
| 翻用例（下一条，含祖先链展开+滚动） | ~31ms/次 | 优秀 |
| 搜索宽泛词（29686 全命中 → 截断 300 入树） | ~780ms | 可接受（防抖 300ms 后一次性成本） |
| **清空搜索**（切回非搜索态） | 优化前 ~2.1s → **优化后 ~0.78s** | **P3 唯一上码项**，见下 |
| 可疑跳转（全量扫描 29686 例） | ~250ms | 良好 |
| 全部已核对（29686 个 reactive 赋值+存档） | ~1.9s | 低频操作，接受 |

**实施项**：[TreeNav.vue](../../web/src/components/TreeNav.vue) 拆出 `baseTree` computed（只依赖 `store.cases`，缓存非搜索态全树）——tree computed 在非搜索态直接复用其缓存（同一批节点对象，TreeLevel 按 key 复用零重渲染），搜索态仍独立建树（命中子集的 caseCount 不同，不能共享节点）。清空搜索的树重建成本全部消除，剩余 ~0.78s 为搜索态↔非搜索态的语义性 DOM 切换（全展开 300 行 ↔ 折叠语义），不可避免。小文档（110 例基线 162 行全展开）与大文档双路径界面回归通过。

**否决项（实测后不需要，避免重复讨论）**：
- **v-virtual-scroll**：树折叠 + 双截断后 DOM 峰值仅 ~2500 节点，虚拟滚动无收益
- **树懒展开**：验证轮已做（v-if 按需渲染 + 大文档默认折叠）
- **分批载入核对**（150 用例分卷）：数据结构不动——实测全部操作 <2s，无必要

**测试环境坑（自动化实测必读）**：Browser pane 隐藏时 Chrome intensive throttling（页面隐藏累计 >5 分钟，reload 不重置）——rAF 不触发、setTimeout 分钟级延迟，App.vue 的 Transition `mode="out-in"` 在该环境下卡 leave 是**伪影**（可见窗口正常，用户场景不受影响）。自动化计时必须用活跃 tab（Playwright 独立浏览器验证通过）。

## 七、风险与回退

| 风险 | 缓解 |
